# ADR 0001 — PTLT 定位为自用工具，不作为产品

- **状态**：已接受
- **日期**：2026-08-09

## 背景

PTLT（Personal Time & Learning Tracker）是一个 workspace 级多租户的个人时间、学习与系统稳定度
追踪系统。截至 2026-08-09，它已实现 SDD 中 Phase 0–2 的绝大部分：109 个 Java 源文件、14 张表、
47 个端点、6 个前端页面。最后一次代码改动是 2026-05-03，此后停滞约三个月。

它的多租户模型（workspace + OWNER/EDITOR/VIEWER）、乐观锁、软删除、同步游标等设计，明显是按
"可能要做成多人产品"的方向搭的。这份 ADR 要回答的问题是：该不该继续朝那个方向走。

## 决策

**把 PTLT 当作自用工具完成，不投入把它做成商业产品。**

保留已有的 workspace 多租户结构（它已经写好且正确，拆掉的成本高于留着），但不再为"多人协作"
或"对外销售"新增功能。

## 理由

### 市场

个人时间/习惯追踪是一个增长但极度拥挤、且几乎不付费的品类：

- 习惯追踪市场约 $2.22B（2026）→ $6.41B（2034），CAGR 14.2% —— 增长是真的。
- 但绝大多数产品免费，付费仅解锁边缘功能；Toggl、RescueTime、Sunsama、Amazing Marvin、
  Notion 模板等已占满各个细分。
- 独立开发者在这个品类的获客能力接近零：没有分发渠道，没有品类内的差异化理由。

对照 ContentFlow 那次战略重置总结出的筛选标准（见该仓库的
`docs/STRATEGIC_RESET_2026.md`），PTLT 在几乎每一条上都不达标：AI 出现之前不存在痛苦到要付费的
工作流；没有人已经在为这个结果付钱；输入不是"混乱的真实世界数据"；出错没有成本；不存在
监管、财务或客户压力。

### 但作为自用工具，它离"真能用"很近

审计（`docs/AUDIT_2026_08_09.md`）显示后端质量不差：多租户隔离实现正确，14 张表结构合理，
47 个端点大多是真实业务逻辑而非脚手架。真正缺的是**一个 `DailyRecord` 录入页** ——
稳定度分数、两个 streak、Dashboard 图表、整个 Analytics 页全部依赖它，而没有任何前端页面能创建它。

补上那一个页面，再处理掉 sync（要么实现要么删除），这个项目就从"跑不起来的骨架"变成
"每天真能用的工具"。估计 2–3 天。

## 后果

**继续做的**

- `DailyRecord` 录入页（最高优先级，一次解锁四块已完成的功能）
- 修掉审计里影响日常使用的缺陷：前端 refresh token（每 15 分钟强制登出）、乐观锁、
  console 打印 bearer token
- 保持 CI 绿，保持后端测试

**不做的**

- 不做多人协作、邀请流、团队计费
- 不做移动端 App
- 不做数据导出/导入的产品化包装
- 不为"卖给别人"做任何 UI 打磨
- 不继续 SDD 里的 Phase 4（`insight` 模块，AI 洞察）—— 那正是 ContentFlow 已经验证过
  没有护城河的方向

**保留但不扩展的**

- workspace 多租户与 RBAC：已写好且正确，留着无成本，拆掉反而要动 47 个端点
- sync 模块：目前 `push` 返回 501，`pull` 只覆盖 14 张表中的 2 张。单机自用不需要同步；
  除非真的要用第二台设备，否则不投入

## 重新考虑的触发条件

出现以下任一情况，再回来重新评估：

- 有人（不是自己）主动要求使用它，并说明是为解决什么问题
- 自己连续三个月每天真实使用，且明确指出某个缺失功能挡住了工作流
- 出现一个把它接入真实业务系统（日历、Git、工时/发票）的具体理由 —— 那会把它从
  "又一个习惯追踪器"变成有数据入口的工具，也就同时改变了上面的市场判断

在此之前，不为假想用户写代码。

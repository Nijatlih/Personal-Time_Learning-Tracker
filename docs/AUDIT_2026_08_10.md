# 审计报告 — 2026-08-10（第二轮）

首轮审计（[`AUDIT_2026_08_09.md`](AUDIT_2026_08_09.md)）留下 14 条未修缺陷。本轮是对**首轮遗漏**的
第二次排查，不是重复上一轮。

**方法**：7 个只读 agent 按维度分工扫（JPA↔schema 保真度、认证与 Spring Security、租户隔离与 RBAC、
业务逻辑与算术、前端、构建与 CI、静默失败与 API 语义）；每个维度的结论再交给一个**对抗式验证 agent**

检查哪些文件没人读过、哪类缺陷结构性缺席。

**结果：27 条候选 → 21 条确认为新缺陷，4 条被驳回，2 条判定为已知项的重述。**

首轮那句"多租户隔离实现正确、问题集中在认证层"的结论，本轮特意去伪证，**结论成立** ——
没有发现新的 IDOR。但首轮漏掉了一整类缺陷：**前后端 DTO 契约不匹配**。

## 1. 本轮最重要的一条

**Routines 页的「Check In」按钮从未成功过一次。**

`frontend/src/pages/Routines.jsx:82` 发的是 `{routineDefinitionId, completedAt}`，
而 `RoutineCompletionRequest` 要的是 `{routineDefinitionId, date, completed}` —— `completedAt`
这个字段后端根本不存在，而两个真正 `@NotNull` 的字段一个都没发。控制器上有 `@Valid`，
所以每次点击都在进 service 之前就被 400 挡掉，页面弹 `Failed to record habit: Invalid input`。

为什么这条比它看起来更严重：routine 完成是稳定度分数里 **40 分**（morning 20 + evening 20）的
唯一来源，而 `StabilityService` 是从 `routine_completions` 表反查的。这张表因此一直是空的。
也就是说 —— **即使补上首轮列为第一优先级的 `DailyRecord` 录入页，稳定度分数里的
morning/evening 两项也永远是 0**，满分只能到 60。

陈旧 SPA（`src/main/resources/static/app.js` 的 `completeRoutine()`）发的是同一个错误 payload，
所以这个 bug 在两个前端里各有一份。

## 2c. 修复过程中新发现的一条（两轮审计都没抓到）

**refresh token 在同一秒内重复签发会撞唯一约束。**

`JwtUtil.generateRefreshToken` 产出的 JWT 内容只有 `sub` + `type` + `iat` + `exp`，而 JWT 的
`iat`/`exp` 只精确到秒。同一个用户在同一秒内签发的两个 refresh token 因此是**逐字节相同**的字符串，
而 `refresh_tokens.token` 上有 `UNIQUE` 约束 —— "登录之后立刻刷新"这条完全正常的时序会直接失败：

```
duplicate key value violates unique constraint "refresh_tokens_token_key"
```

此前表现为 500（被 catch-all 吞成 "An unexpected error occurred"），补上 `DataIntegrityViolation`
处理器之后表现为 409。两种都不对 —— 真正的问题是 token 本身没有唯一性。修法是两种 token 都加随机 `jti`。

这条是在验证提交 5 的刷新流程时撞出来的，说明**真跑一次**比读代码能发现的东西更多。

## 3. 已排除 —— 下一轮不要再查

对抗式验证驳回的，以及专门去查但确认干净的。记在这里是为了不重复劳动。

- **实体 ↔ schema 无任何不匹配。** 14 个实体对 4 个迁移逐列比过（agent 一遍、手工一遍）：
  6 个枚举全是 `@Enumerated(EnumType.STRING)` 且取值与 SQL 的 CHECK 约束完全一致
  （`WorkspaceRole`/`RoutineType`/`TaskStatus`/`StabilityStatus`/`CognitiveEnergy`/`AlertType`）；
  `@Version` 字段与 version 列一一对应；`alerts` 和 `bootcamp_modules` 少 version/updated_at
  是实体与 SQL 双方一致地少；`ScheduleSlot.dayOfWeek` 用 JDK 的 `DayOfWeek`，最长值
  `WEDNESDAY`（9 字符）能装进 `VARCHAR(10)`。**`ddl-auto: validate` 能过。**
- **4 个迁移从空库重放是自洽的** —— 每个 `REFERENCES` 指向的表都在同文件或更早的文件里建过。
- **`RefreshTokenRepository` 的 UPDATE/DELETE 查询都带 `@Modifying`** —— 后端 logout 的撤销逻辑
  本身是有效的（真正的问题是前端从不调用它，见 F5 那一批）。
- **VIEWER/EDITOR 在写路径上确实没被强制**（`TaskService.validateWorkspaceAccess` 等只查成员身份
  不查角色）—— 代码事实成立，但按 ADR 0001 不做协作，本轮的处理是删掉整套死代码而不是补校验。
- 软删除与唯一约束的交互（软删后重建会撞 UNIQUE）：验证 agent 逐个追踪 6 张表的软删路径后判为不可达。
- sync pull 把同 workspace 成员的 userId/role 返给成员：同租户数据，非越权。
- **Jackson 序列化干净**：没有任何双向 JPA 关联（每个外键都是裸 `UUID` 列），所以不存在无限递归；
  日期走 Boot 默认的 jsr310 ISO-8601；没有自定义 `ObjectMapper` 覆盖默认值。
- **无共享可变状态**：全部 service 是无状态单例，只注入 final repository，没有 static 可变字段。
- **请求校验覆盖完整**：10 个 controller 里每个收 `@RequestBody` 的方法都有 `@Valid`。
- `frontend/vite.config.js:11` 的 `changeOrigin` **是正确的 Vite 选项名**，不是拼写错误。
- `DailyRecordRepository.findByWorkspaceIdAndDateRange` 是 `ORDER BY date DESC`，
  所以 `DashboardService:68` 的 `recentRecords.get(0)` 取的确实是最新一条 —— 曾怀疑是排序 bug，不是。
